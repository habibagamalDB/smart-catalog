# 0007. Internationalization and RTL

Status: Accepted (2026-11-05)

## Context

The primary audience reads Arabic; some customers and merchants prefer English. Layouts must mirror correctly, and both the UI and bakery content must be bilingual.

## Decision

- next-intl with locales `ar` (default) and `en`, always prefixed in the URL (`/ar/...`, `/en/...`). The proxy negotiates the locale from the browser's `Accept-Language` header and cookie.
- The root layout lives in `app/[locale]` and reads the locale with `next/root-params`. It sets `lang` and `dir` on `<html>` and wraps the app in Radix's `Direction.Provider`.
- UI strings live in `messages/{ar,en}.json`; a unit test keeps their keys identical. Message types are checked through next-intl's `AppConfig`.
- Bakery content uses paired columns (`name_ar`, `name_en`, and so on), falling back to the other language when one is empty.
- Styling uses Tailwind logical utilities (`ms-*`, `pe-*`, `start-*`), never physical left/right.
- Fonts: IBM Plex Sans Arabic for Arabic and Geist for Latin, with the order swapped by `:lang(ar)`.
- Unmatched URLs render a bilingual `global-not-found` page, because the root layout sits under a dynamic segment.

## Consequences

- Adding a third language later means adding columns or moving to translation tables; acceptable given the target market.
